# 项目 5：个人「时间电网」调度器

> 把个人日程管理建模为电网经济调度（Unit Commitment / Economic Dispatch）问题：
> **任务 = 负载**（工期、截止时间、可中断性），**精力 = 发电曲线**（昼夜节律，可自我标定），**会议 = 不可中断基荷**。
> 用真正的最优化求解器编排一天/一周的日程，而不是手动拖拽方块。

---

## 1. 一句话定位与目标用户

**一句话定位**：一个端侧运行的「日程求解器」——你只声明任务和约束，它用 CP-SAT 算出一份与你精力曲线匹配、深度工作块最大化的可执行时间表。

**目标用户**（按优先级）：

| 优先级 | 人群                             | 痛点                                                         |
| ------ | -------------------------------- | ------------------------------------------------------------ |
| P0     | 知识工作者 / 独立开发者 / 研究生 | 任务多、会议碎片化，深度工作时间被切碎；常把难活排在精力低谷 |
| P1     | 自由职业者                       | 多项目并行 + 硬截止时间，需要"哪个先做"的最优答案而非直觉    |
| P2     | ADHD / 执行功能弱的用户          | 无法自己做排程决策，需要外部系统直接给出"现在做什么"         |

**反目标用户**：销售/客服等日程完全被外部驱动的人（无可调度空间），团队排程场景（这是另一个产品）。

**差异化**：现有工具（Motion、Reclaim.ai）是云端黑盒启发式；本项目 (a) 端侧求解、数据不出设备，(b) 优化目标可解释、可选择，(c) 把"精力"作为一等公民建模，而不只是时间。

## 2. MVP 范围（是否先不做日历集成？）

**建议：MVP 阶段不做双向日历集成，只做单向 ICS 导入 + ICS 导出。**

理由：

1. Google Calendar OAuth + 双向同步（冲突解决、增量同步、token 刷新）是工程黑洞，至少 2~3 周，但对验证核心假设（"求解器排出的日程比手排好"）零贡献。
2. ICS 是纯文本格式，导入解析约 1 天工作量，即可拿到真实会议数据当基荷；导出 `.ics` 让用户一键订阅回自己的日历，体验闭环已成立。
3. 端侧优先原则下，ICS 文件拖拽导入天然无需服务器。

**MVP 范围（In）**：

- 任务录入：标题、工期估计、截止时间、可中断性（可拆 / 不可拆）、最小块时长、优先级（3 档）
- 会议导入：拖拽 `.ics` 文件 → 解析为基荷（也支持手动添加）
- 精力曲线：3 个预设模板（早鸟 / 夜猫 / 双峰）+ 滑块微调（见 §5）
- 求解：当天 + 未来 7 天，时间粒度 15 分钟，两个目标函数二选一
- 输出：时间网格视图（类电网调度甘特图，叠加精力曲线背景色）+ `.ics` 导出
- 重排：任意修改后一键重新求解（"re-dispatch"）
- 全部端侧：PWA，数据存 IndexedDB

**MVP 范围（Out，明确不做）**：

- Google/Outlook OAuth 双向同步（v1.1）
- 多人协作、共享日历
- 自动时间追踪 / 番茄钟（可手动标记"完成"即可）
- 移动原生 App（PWA 顶上）
- AI 自然语言录入任务（v1.x 锦上添花）

## 3. 调度问题形式化建模

### 3.1 离散化与记号

把调度地平线 $H$（如未来 7 天的清醒时间）离散为时隙集合 $T = \{0, 1, \dots, |T|-1\}$，每个时隙 $\Delta = 15$ 分钟。一天清醒 16 小时 → 64 槽/天，7 天 ≈ 448 槽。

- 任务集合 $J$，每个任务 $j$ 有：
  - 工期 $p_j \in \mathbb{Z}^+$（槽数）
  - 截止时隙 $d_j$（可为软截止）
  - 释放时隙 $r_j$（最早可开始）
  - 可中断标志 $\text{splittable}_j \in \{0,1\}$，最小连续块长 $m_j$（如 2 槽 = 30 分钟）
  - 认知负载等级 $\ell_j \in \{1,2,3\}$（轻 / 中 / 深度）
  - 优先级权重 $w_j$
- 会议集合 $M$：固定区间 $[s_k, e_k)$，占用对应时隙且消耗精力 $c_k$
- 精力曲线 $E: T \to [0, 100]$，由标定模块给出（§5），是**参数**而非变量

### 3.2 决策变量（CP-SAT 形式）

对不可中断任务 $j$：

- 区间变量 $\text{itv}_j = \text{IntervalVar}(\text{start}_j,\ p_j,\ \text{end}_j)$

对可中断任务 $j$：拆为 $n_j = \lceil p_j / m_j \rceil$ 个段（segment），每段一个**可选区间变量**：

- $\text{itv}_{j,s} = \text{OptionalIntervalVar}(\text{start}_{j,s},\ \text{len}_{j,s},\ \text{end}_{j,s},\ \text{pres}_{j,s})$，$\text{len}_{j,s} \in [m_j,\ p_j]$

辅助变量：

- $x_{j,t} \in \{0,1\}$：任务 $j$ 是否占用时隙 $t$（仅在目标函数需要逐槽精力账本时物化；否则用区间推理避免 $|J| \times |T|$ 的变量爆炸）
- $L_t \in \mathbb{Z}$：时隙 $t$ 的总认知负载（见约束 C6）
- $\text{tard}_j \geq 0$：软截止的延误量

### 3.3 约束

- **C1 互斥（单机）**：所有任务区间 + 会议区间满足 `NoOverlap`（人是单核处理器）。
- **C2 基荷固定**：会议区间为常量区间，参与 NoOverlap 但不可移动。
- **C3 时间窗**：$\text{start}_j \geq r_j$；硬截止任务 $\text{end}_j \leq d_j$；软截止任务 $\text{tard}_j \geq \text{end}_j - d_j$。
- **C4 工期守恒（可中断）**：$\sum_s \text{pres}_{j,s} \cdot \text{len}_{j,s} = p_j$，且每段 $\geq m_j$。
- **C5 段间最小间隔与顺序（可选）**：$\text{start}_{j,s+1} \geq \text{end}_{j,s}$，消除对称解、加速求解。
- **C6 精力可行性（机组爬坡的类比）**：深度任务（$\ell_j = 3$）只能排在 $E(t) \geq \theta_{\text{deep}}$（如 65）的时隙：对每个深度任务段，限制其 start/end 落在高能区间的并集内（用 `AddAllowedAssignments` 或区间域裁剪实现，避免逐槽布尔变量）。
- **C7 休息约束**：连续工作（任务 + 会议）超过 $K$ 槽（如 6 槽 = 90 分钟）必须插入 $\geq 1$ 槽空闲——电网类比是"机组最小停机时间"。实现：对滑动窗口加 `sum ≤ K` 约束，或用正则约束（Automaton）。
- **C8 日界与睡眠**：睡眠时段时隙直接从域中删除（不建变量），缩小问题规模。

### 3.4 目标函数（二选一，UI 切换）

**目标 A：最小化精力峰谷差（负载平滑 / peak shaving）**

定义时隙净压力 $S_t = \text{load}(t) - E(t)$，其中 $\text{load}(t) = \sum_j \ell_j \cdot x_{j,t} + \sum_k c_k \cdot \mathbb{1}[t \in M_k]$。

$$\min\ \alpha \cdot \big(\max_t S_t - \min_t S_t\big) + \beta \sum_j w_j \cdot \text{tard}_j$$

直觉：不让任何时段"超发"（高负载撞低精力），也不让高能时段空转。CP-SAT 用 `AddMaxEquality` / `AddMinEquality` 实现。此目标需要物化 $x_{j,t}$，是两者中较贵的。

**目标 B：最大化深度工作连续块（推荐为默认）**

$$\max\ \sum_{j:\ell_j=3} \sum_s \text{pres}_{j,s} \cdot \big(\text{len}_{j,s}\big)^{+} \cdot u(E_{\text{avg}}(\text{itv}_{j,s})) \;-\; \beta \sum_j w_j \cdot \text{tard}_j \;-\; \gamma \cdot \text{nSegments}$$

其中 $(\cdot)^+$ 表示对块长做超线性奖励（分段线性近似：90 分钟块的价值 > 3 个 30 分钟块之和），$u(\cdot)$ 为精力匹配系数，$\gamma$ 惩罚碎片数。直觉：奖励"长块 × 高能时段"的乘积，惩罚切碎和拖延。

**软硬分层**：硬约束（截止、会议、睡眠）不可违反；目标内各项用字典序或加权和（$\alpha, \beta, \gamma$ 暴露为高级设置，默认值经验给定）。

### 3.5 复杂度评估

7 天 × 64 槽、30 个任务、可中断任务平均拆 4 段 ≈ 120 个区间变量 + NoOverlap。这是 CP-SAT 的舒适区，目标 B 下预计亚秒~数秒可得高质量解；目标 A 因需逐槽变量（~$30 \times 448$ 布尔）会慢一些，可限定为"仅当天 + 明天"两天窗口求解、其余天用滚动时域（receding horizon）。

## 4. 求解器选型

| 方案                                   | 优点                                                                       | 缺点                                                                         | 结论            |
| -------------------------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | --------------- |
| **OR-Tools CP-SAT（原生 Python/C++）** | 区间变量 + NoOverlap 是为此类问题量身定做；免费工业级；可行解 + 最优性间隙 | 官方无 JS/WASM 发行版 → 端侧用不上，需要服务器，违背端侧原则                 | 仅作离线基准    |
| **CP-SAT 编译为 WASM**                 | 理论上端侧最强                                                             | 自行编译 OR-Tools C++ → WASM 工程量大、产物 >20MB、维护成本高，单人不可承受  | 放弃            |
| **MILP（HiGHS WASM，`highs-js`）**     | HiGHS 有现成 WASM 包（约 2~3MB），MILP 建模目标 A 自然                     | 区间/NoOverlap 需手写 big-M 析取约束，模型臃肿；可中断任务的 MILP 编码易爆炸 | 备选            |
| **JS 启发式 + 局部搜索（自研）**       | 零依赖、毫秒级、完全可控                                                   | 无最优性保证，复杂约束组合下容易排出违约解，"真优化"卖点打折                 | 作为兜底/初始解 |
| **Timefold / OptaPlanner**             | 排程领域专用                                                               | JVM 系，端侧不可行                                                           | 放弃            |

**推荐：分层混合架构（端侧优先）**

1. **第 0 层（即时反馈）**：自研贪心构造启发式 —— 按 $w_j / (d_j - r_j)$ 紧迫度排序，深度任务优先抢占高能时段，<10ms 出一份可行解，UI 立即渲染。
2. **第 1 层（端侧精解，主力）**：**HiGHS WASM（highs-js）跑 MILP**，以贪心解作 warm start，Web Worker 内限时 5 秒，时限到取当前最好解。MVP 只对"当天 + 明天"精解，后面 5 天用启发式滚动填充。
3. **第 2 层（可选离线校验，仅开发期）**：本地 Python + OR-Tools CP-SAT 作为黄金基准，验证 MILP 编码正确性与启发式的最优性间隙（目标值差距），不进产品。

**MVP 落地顺序**：先只做第 0 层（启发式）打通全链路 → Phase 2 引入 highs-js。若后续 Google 发布官方 CP-SAT WASM（值得每季度关注一次），直接替换第 1 层。

## 5. 精力曲线自我标定机制

原则：**输入成本必须接近零**，否则没人标定。三级递进：

**Level 0 — 模板冷启动（10 秒）**
首次启动问 2 个问题："你几点自然醒？""一天中最清醒的时段？"→ 映射到 3 条预设曲线之一（早鸟峰 9–12 点 / 夜猫峰 20–24 点 / 双峰 10 点 + 16 点），曲线为 24 点分段线性插值。

**Level 1 — 拖拽微调（30 秒，可选）**
设置页展示曲线，用户直接拖动 4~6 个控制点（醒来爬升斜率、上午峰值、午后谷深度与时间、晚间二次峰）。比逐小时打分友好得多。

**Level 2 — 被动标定（持续，核心机制）**
每次用户标记任务"完成"时，弹一个**单击即走**的微调查："刚才状态如何？🔥 / 😐 / 🥱"（点击或忽略，无文字输入）。数据点 $(t, \text{rating})$ 累积后：

- 用按周几分组的核回归（或简单的 24 桶指数移动平均）更新曲线：$E_{\text{new}}(t) = (1-\eta) E_{\text{old}}(t) + \eta \cdot \text{rating}_t$，$\eta \approx 0.15$；
- 区分工作日/周末两条曲线；
- 样本 < 10 个时不覆盖模板，只做混合，避免噪声驱动。

**Level 3 — 行为信号（v1.x，不进 MVP）**：用"深度任务实际完成时长 vs 估计时长"的比值作为隐式精力信号；可穿戴设备（HRV/睡眠）导入留接口。

**反馈闭环展示**：曲线页标注"基于你最近 N 次反馈"，让用户看到标定在生效——这是留存钩子。

## 6. 与现实的接口（Calendar / ICS）

**MVP（单向，零服务器）**：

- **导入**：拖拽 `.ics` 文件或粘贴 ICS 订阅 URL（经浏览器 fetch，注意 CORS——提供"下载后拖入"作为兜底）。解析库用 `ical.js`（Mozilla，成熟）。导入事件一律视为不可移动基荷；全天事件询问是否占用精力。RRULE 循环事件展开到调度地平线即可，不必完整实现 RFC 5545。
- **导出**：求解结果生成 `.ics` 文件下载（每个任务块一个 VEVENT，UID 带任务 ID 后缀以便重排后覆盖）。用户导入自己的 Google/Apple 日历，即可在手机上看到计划。

**v1.1（双向，可选登录）**：

- Google Calendar API：增量同步（syncToken）拉会议，写回一个**专用日历**"Time Grid Plan"（绝不写用户主日历，重排时整删整建该日历，规避冲突解决难题）。
- OAuth token 存端侧（PKCE flow，无后端密钥），坚持无服务器架构。
- Outlook/CalDAV 视需求再说。

**现实接口的产品规则**：

- 计划赶不上变化：任何已过去的时隙自动锁定为历史，重排只动未来——"滚动时域调度"。
- 新会议进来（重新导入 ICS）→ 提示"基荷已变化，重新调度？"一键 re-dispatch。

## 7. 里程碑（4 阶段）

**Phase 1：求解核心验证（第 1–2 周）**

- 交付物：TypeScript 数据模型（Task/Meeting/EnergyCurve/Schedule）+ 贪心启发式求解器 + 20 个固定场景的快照测试（含：截止冲突、会议密集日、深度任务挤压）
- 验证标准：所有场景产出零硬约束违反的可行解，单元测试绿；离线 Python CP-SAT 基准脚本就绪，记录启发式最优性间隙

**Phase 2：端侧精解 + 最小 UI（第 3–4 周）**

- 交付物：highs-js MILP 编码（目标 B）跑在 Web Worker；时间网格视图（精力曲线背景 + 任务块）；任务 CRUD；IndexedDB 持久化
- 验证标准：30 任务 / 2 天窗口在 5 秒内出解且目标值 ≥ 启发式；UI 可完成"录任务 → 求解 → 看网格"全流程

**Phase 3：现实接口 + 标定闭环（第 5–6 周）**

- 交付物：ICS 导入/导出；Level 0–2 精力标定（模板 + 拖拽 + 完成时微调查）；重排（re-dispatch）与时隙锁定；PWA 离线可用
- 验证标准：用自己的真实日历**自用（dogfood）连续 5 个工作日**，记录"计划遵守率"（按计划执行的块 / 总块数）

**Phase 4：打磨与小范围发布（第 7–8 周）**

- 交付物：双目标切换 + 求解结果解释（"为什么把 X 排在 14:00"——展示绑定约束）；onboarding 流程；落地页；发布到 5–10 个种子用户
- 验证标准：≥5 名外部用户完成 3 天以上使用；遵守率与 NPS 数据回收；据此决定 v1.1 是否做 Google 双向同步

## 8. 主要风险与对策

1. **过度优化导致用户不遵守计划（最大风险）**
   求解器排出"数学最优"但人不执行的日程（块太满、转场太硬、不留弹性），用户失败两次就弃用，产品死于"计划-现实鸿沟"。
   **对策**：(a) 内置松弛——默认只调度每日可用时间的 70%，任务间强制 15 分钟缓冲（作为硬约束 C7 的一部分）；(b) 把"遵守率"作为北极星指标而非目标函数值，dogfood 期间专门追踪；(c) 提供"宽松度"滑块（实质是调 70% 这个参数）；(d) 重排零摩擦——偏离计划后一键 re-dispatch 且**不展示任何负面反馈**（绝不显示"你落后了"），调度器的人设是冷静的电网调度员，不是监工；(e) 求解时加"计划稳定性"惩罚项：重排时偏离上一版计划的任务移动量进目标函数，避免每次重排面目全非引发不信任。

2. **WASM 求解器性能不达标 / 包体过大**
   highs-js 在低端设备上 5 秒出不了好解，或 3MB WASM 拖慢首屏。
   **对策**：分层架构本身就是兜底——启发式永远先出可行解，精解是渐进增强；WASM 懒加载（首次求解时才拉取并缓存于 Service Worker）；缩小精解窗口到 2 天；Phase 2 设硬性性能门槛，不达标则启发式 + 局部搜索（模拟退火）顶替，产品叙事从"最优"调整为"近优"。

3. **工期估计不准（garbage in, garbage out）**
   用户系统性低估工期（规划谬误），再好的求解器也排出虚假日程。
   **对策**：录入时只提供粗粒度选项（30m / 1h / 2h / 半天），拒绝精确到分钟的假精度；记录"实际 vs 估计"比值，对每用户做估计膨胀系数（如 ×1.4）自动校正；UI 标注"含你的历史校正"。

4. **精力曲线标定数据稀疏 / 噪声大**
   用户忽略微调查，或情绪性打分污染曲线，导致深度任务被排进伪高能区。
   **对策**：模板先验 + 贝叶斯式混合（样本少时模板权重高）；微调查做成可完全忽略且不阻塞流程；曲线更新用小学习率 EMA 抗噪；设置页可一键重置回模板。

5. **ICS 解析的现实复杂度**
   时区（VTIMEZONE）、RRULE 例外（EXDATE）、Outlook 导出的非标字段，解析失败导致基荷缺失 → 排程撞会议，信任崩塌。
   **对策**：用 ical.js 而非自研；解析失败的事件显式列出让用户手动确认而非静默丢弃；MVP 只承诺支持 Google/Apple 导出的 ICS，其余标注 beta；收集失败样本建回归测试集。

6. **单人项目范围蔓延**
   优化爱好者容易沉迷建模（多目标 Pareto、随机规划、鲁棒优化……），产品永远到不了用户手里。
   **对策**：§2 的 Out 清单具有否决权；每个 Phase 末有硬性"可验证交付物"；建模花哨度冻结在 §3 的版本，新想法一律进 v2 backlog。

## 9. 第一周行动清单（具体到天）

> 目标：周末时拥有一个能在固定测试场景上排出可行日程的求解核心 + 离线基准。技术栈：Vite + TypeScript + Vitest（纯前端，本周无 UI）。

- **周二 — 测试场景库**
  手写 8 个 JSON 测试场景（轻载日、会议密集日、双硬截止冲突、深度任务 × 夜猫曲线、不可拆长任务、全可拆碎任务、超载不可行日、跨 7 天滚动），每个场景附"人类合理排法"注释作对照；写场景加载器与可行性校验器（检查 C1–C8 全部约束的独立 validator——它同时是日后所有求解器的裁判）。

- **周三 — 贪心启发式 v0**
  实现构造式启发式：按紧迫度 $w_j/(d_j - \text{now})$ 排序 → 深度任务优先占据高能时隙 → 可拆任务填缝；跑通 8 个场景，validator 全绿；记录每个场景的目标 B 函数值（手写目标值计算器）。
