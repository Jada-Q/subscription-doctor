# 项目 2：用麦克风做的「万物频谱仪」

> 纯浏览器 PWA · Web Audio API + 端侧 DSP · 零硬件成本 · 单人可执行

---

## 1. 一句话定位与目标用户

**一句话定位**：把手机麦克风变成口袋里的声学诊断仪——敲一敲、听一听，就能判断杯子有没有裂、轴承磨没磨损、吉他调没调准，所有分析全部在浏览器本地完成，不装 App、不传数据。

**目标用户（按优先级）**：

| 优先级 | 人群                          | 场景                   | 付费/传播潜力                    |
| ------ | ----------------------------- | ---------------------- | -------------------------------- |
| P0     | 吉他/尤克里里玩家（含初学者） | 调音 + 琴颈健康诊断    | 基数大、需求高频、易传播         |
| P1     | 二手交易买家、装修验收者      | 敲瓷砖/杯子/陶瓷验裂纹 | 强分享性（"敲一敲就知道"很魔性） |
| P2     | 设备维护爱好者、DIY 玩家      | 风扇/轴承/硬盘异响诊断 | 小众但忠诚，内容素材丰富         |
| P3     | 物理/工程教育者               | 课堂演示模态分析、FFT  | 长尾，带来权威背书               |

**核心价值主张**：专业声学检测设备（模态锤 + 加速度计 + 频谱仪）动辄数万元，本项目用"已经在你口袋里的传感器"覆盖其中 70% 的日常场景，且隐私零风险（音频不离开设备）。

## 2. MVP 范围：先做一个杀手场景

### 选择：**吉他自动调音 + 琴颈变形诊断**

三个候选场景的对比：

| 维度             | 吉他调音+琴颈诊断                      | 敲击验裂纹                 | 轴承边带分析               |
| ---------------- | -------------------------------------- | -------------------------- | -------------------------- |
| 用户基数         | 极大（调音器是刚需）                   | 中                         | 小                         |
| 真值可验证性     | **强**（音准有客观标准，调音对错立判） | 弱（需要砸开才能确认裂纹） | 弱（需拆机确认磨损）       |
| 算法风险         | 低（基频估计是成熟问题）               | 中（依赖指纹库，冷启动难） | 高（边带淹没在宽带噪声里） |
| 麦克风频响敏感度 | 低（只关心频率位置，不关心幅度）       | 高                         | 高                         |
| 留存抓手         | 高频使用（每次弹琴前都要调音）         | 一次性                     | 低频                       |
| 差异化           | 调音器满大街，但**琴颈诊断没人做**     | 强                         | 强                         |

**选择理由（三点）**：

1. **可验证闭环最短**。调音结果当场可被用户耳朵和其他调音器验证，建立信任后再引导用户使用"软指标"场景（裂纹/磨损）。反过来不行——如果第一印象是一个无法验证的"玄学检测"，产品就死了。
2. **算法去风险**。基频估计（YIN/自相关）是教科书级问题，一周内可做到商用精度；而裂纹检测依赖尚不存在的指纹库（见第 6 章），把它放 MVP 等于把数据冷启动问题放在了产品冷启动前面。
3. **琴颈诊断是钩子**。普通调音器只告诉你"E2 偏低 12 音分"，我们额外做：弹空弦后分析谐波列的**不谐和度（inharmonicity）**与各品衰减一致性，提示"琴颈可能前弓过度/品丝不平"——这是免费调音器红海里唯一的差异化叙事，也是技术上模态分析的"简化预演"。

### MVP 功能清单（做）

- 实时频谱仪 + 瀑布图（所有场景的公共底座，本身就有可玩性）
- 六弦标准调音（E2 A2 D3 G3 B3 E4）+ 半音模式，精度 ±1 音分
- 琴颈诊断（Beta 标签）：空弦谐波不谐和度分析 + 12 品泛音/按音对比引导流程，输出"弦距/琴颈"建议
- PWA 离线可用、加到主屏幕
- 麦克风校准向导（播放已知扫频信号给用户参考 + 机型频响数据库雏形，见第 8 章）

### MVP 不做（写下来防止蔓延）

- 裂纹检测、轴承诊断（Phase 3/4 再上，以"实验室"入口预埋）
- 任何账号系统、云端存储
- 小波分析（MVP 用 STFT 足够，小波留给敲击瞬态场景）
- 原生 App、WebView 套壳

## 3. 技术架构

### 3.1 总体分层

```
┌────────────────────────────────────────────────────┐
│  UI 层 (React/Preact + Canvas/WebGL)               │
│  调音表盘 · 瀑布图 · 诊断报告卡片                      │
├────────────────────────────────────────────────────┤
│  应用层 (主线程)                                     │
│  场景状态机 · 结果聚合 · 指纹库匹配 · IndexedDB        │
├────────────────────────────────────────────────────┤
│  DSP 层 (AudioWorklet + Worker)                     │
│  AudioWorklet: 采集/分帧/环形缓冲 (128 帧粒度)        │
│  Worker(+WASM): FFT · YIN · 倒谱 · 包络解调 · 小波   │
├────────────────────────────────────────────────────┤
│  采集层 (Web Audio API)                             │
│  getUserMedia({ echoCancellation:false,             │
│    noiseSuppression:false, autoGainControl:false }) │
└────────────────────────────────────────────────────┘
```

### 3.2 关键技术决策

**决策 1：必须用 AudioWorklet，不用 ScriptProcessorNode**
ScriptProcessorNode 已废弃且在主线程跑，掉帧即丢数据。AudioWorklet 在独立渲染线程以 128 sample 为单位回调，把样本写入 `SharedArrayBuffer` 环形缓冲（退化方案：`postMessage` 转移 `ArrayBuffer`，见下）。Worklet 内**只做搬运和最轻量的预处理（DC 去除）**，重计算全部丢给 Worker，避免阻塞音频线程。

注意：`SharedArrayBuffer` 需要 COOP/COEP 头（crossOriginIsolated）。PWA 静态托管（Vercel/Cloudflare Pages）配置响应头即可，但这会限制第三方 iframe——本项目无此需求，可放心开启。Safari 16.4+ 支持，需保留 `postMessage` 降级路径。

**决策 2：AnalyserNode 只用于"好看"，不用于"诊断"**
内置 `AnalyserNode.getFloatFrequencyData()` 拿来画装饰性实时频谱足够（零成本），但它窗函数固定（Blackman）、无法控制 hop size、无法做重叠加窗，**所有出诊断结论的数据必须走自己的 FFT 管线**。这一条写进代码注释和 PR checklist。

**决策 3：WASM FFT 的取舍 —— 先 JS，预留接口，按基准测试决定是否切换**

| 方案                           | 4096 点 FFT 耗时（中端手机，估） | 结论                        |
| ------------------------------ | -------------------------------- | --------------------------- |
| 纯 JS（fft.js / 自写 radix-2） | ~0.3–0.8 ms                      | MVP 完全够用                |
| WASM（PFFFT / KissFFT 编译）   | ~0.05–0.2 ms                     | 量级提升，但有加载/胶水成本 |
| WebGPU compute                 | 更快但兼容性差                   | 不考虑                      |

理由：调音场景每秒约 20–40 次 4096 点 FFT/YIN，纯 JS 在 2019 年后的手机上 CPU 占用 <5%。**WASM 的真正用武之地在 Phase 3/4**：敲击模态分析需要对 1–2 秒录音做高分辨率分析（zoom-FFT、CWT 连续小波，是 O(N·M) 级计算），轴承诊断需要长时 Welch 平均 + 希尔伯特包络。架构上定义统一接口：

```ts
interface DspBackend {
  fft(input: Float32Array): { re: Float32Array; im: Float32Array };
  yin(frame: Float32Array, sampleRate: number): PitchResult;
  cepstrum(input: Float32Array): Float32Array;
}
// js-backend.ts 先行；wasm-backend.ts (PFFFT via Emscripten) Phase 3 接入，
// 以 feature detection + 基准测试动态选择。
```

**决策 4：采集参数纪律**

- `getUserMedia` 三个"音质毁灭者"必须显式关闭：`echoCancellation / noiseSuppression / autoGainControl = false`（AGC 不关，幅度类特征全部作废）。注意部分安卓机型不完全遵守 constraints，需用 `MediaStreamTrack.getSettings()` 回读确认并在 UI 提示。
- 采样率：用设备默认（通常 48 kHz），**不指定**以避免浏览器重采样引入伪影；所有算法以 `AudioContext.sampleRate` 为参数而非硬编码。
- iOS Safari：AudioContext 必须由用户手势启动；切后台会被挂起，监听 `statechange` 做恢复。

**决策 5：PWA 与离线**
Service Worker 预缓存全部静态资源 + WASM 二进制；指纹库（JSON，预计 <2 MB）走 IndexedDB + 版本化增量更新。无任何运行时服务端依赖——这同时是隐私卖点和运维成本卖点（静态托管，月成本 0 元）。

### 3.3 数据流（以调音为例）

```
Mic ──► AudioWorklet（128 帧 → SAB 环形缓冲）
            │
            ▼ (Worker 以 4096 窗 / 75% overlap 拉取)
        DC 去除 → Hann 窗 → ├── YIN 基频估计 ──► 中值滤波(5帧) ─► 音分偏差
                            └── FFT → 谐波峰提取 ──► 不谐和度 B 系数拟合
            │
            ▼ postMessage (节流至 30 fps)
        UI：指针动画(插值) + 瀑布图(WebGL 纹理滚动)
```

## 4. 信号处理算法清单

难度：★ 一天内可完成 ｜ ★★ 一周内 ｜ ★★★ 需要调研+迭代 ｜ ★★★★ 有研究风险

### 公共底座

| 算法                                         | 用途                           | 难度 | 备注                               |
| -------------------------------------------- | ------------------------------ | ---- | ---------------------------------- |
| 分帧 + 窗函数（Hann/Blackman-Harris/平顶窗） | 一切的基础                     | ★    | 平顶窗用于幅度精确读数场景         |
| Radix-2 FFT + Welch 平均                     | 频谱估计、降噪声底             | ★    | Welch 对稳态信号（风扇）必备       |
| 抛物线峰插值                                 | 把 FFT bin 分辨率提升 10–50 倍 | ★    | 三点二次拟合，调音和模态都靠它     |
| 噪声底估计 + 峰显著性检测                    | 自动找峰、抑制误报             | ★★   | 中值滤波谱 + SNR 阈值              |
| A 计权 / 简单声级参考                        | 提示用户"环境太吵"             | ★    | 不做绝对 SPL（无法校准），只做相对 |

### 场景 A：吉他调音 + 琴颈诊断（MVP）

| 算法                                  | 用途                   | 难度 | 备注                                                       |
| ------------------------------------- | ---------------------- | ---- | ---------------------------------------------------------- |
| YIN（或 MPM）时域基频估计             | 调音核心               | ★★   | 比纯 FFT 找峰稳健，低音弦 E2=82 Hz 必须用它；阈值 0.1–0.15 |
| 基频中值滤波 + 滞回显示               | 指针不乱跳             | ★    | UX 关键，算法不值钱但调参值钱                              |
| 谐波列提取 + 不谐和度系数 B 拟合      | 琴颈/弦况诊断          | ★★★  | f_n = n·f₀·√(1+B·n²)，B 异常大提示弦老化/弦距过高          |
| 12 品泛音 vs 按音音准差（引导式流程） | 八度音准→琴颈/琴桥诊断 | ★★   | 算法简单，难在引导用户正确操作                             |
| 衰减时间（T60 式）逐弦估计            | 检测打品/品丝不平      | ★★★  | 能量包络对数斜率拟合                                       |

### 场景 B：敲击验裂纹（模态分析，Phase 3）

| 算法                                           | 用途                       | 难度 | 备注                                              |
| ---------------------------------------------- | -------------------------- | ---- | ------------------------------------------------- |
| 瞬态检测（能量突变 + 谱通量）                  | 自动截取敲击片段           | ★★   | 预触发环形缓冲，截 50ms 前 + 500ms 后             |
| 高分辨率谱估计（zero-padding FFT 或 zoom-FFT） | 模态频率定位               | ★★   | 敲击信号短，分辨率是矛盾核心                      |
| 模态参数提取：峰频率 + 半功率带宽 → 阻尼比 ζ   | **裂纹判据核心**           | ★★★  | 裂纹的最强信号是阻尼骤增（声音"发闷"）+ 模态分裂  |
| 模态分裂检测（单峰 → 双峰）                    | 裂纹特异性指标             | ★★★  | 轴对称物体（杯/碗）裂纹会让简并模态分裂成两个近峰 |
| CWT 连续小波（Morlet）时频图                   | 区分"裂纹闷响"与"手持阻尼" | ★★★★ | WASM 加速的主要客户；也可先用多窗 STFT 近似       |
| 同物多次敲击一致性聚类                         | 降低单次误差               | ★★   | 要求用户敲 3–5 次，取稳定模态                     |

### 场景 C：风扇/轴承磨损（Phase 4）

| 算法                              | 用途                              | 难度 | 备注                                                               |
| --------------------------------- | --------------------------------- | ---- | ------------------------------------------------------------------ |
| 长时 Welch 谱（10–30 s 平均）     | 拉低噪声底，露出边带              | ★★   |                                                                    |
| 倒谱（real cepstrum）             | 检测谐波族/边带的周期性           | ★★★  | 边带间隔在倒谱域是一个峰，比肉眼找边带稳健                         |
| 希尔伯特包络解调 + 包络谱         | 轴承故障特征频率（BPFO/BPFI）检测 | ★★★★ | 经典 envelope analysis；难点是共振带选择（可用谱峭度 SK 自动选带） |
| 转速估计（基频/叶片通过频率反推） | 无转速计时归一化特征频率          | ★★★  | 风扇叶片数已知时 BPF = 叶数 × 转速                                 |
| 峭度 / 峰值因子等标量指标         | "健康分"的可解释成分              | ★    | 冲击性故障早期敏感                                                 |

**算法实施纪律**：每个算法先用 Python/Jupyter + 真实录音验证（仓库内 `research/` 目录），确认有效后再移植 TS/WASM；每个移植算法配对照测试（同一输入，Python 与 TS 输出误差 < 1e-5）。

## 5. UI/UX 设计原则

**原则 1：每个像素要么承载信息，要么引导操作——拒绝"科幻仪表盘"**
实时频谱很容易做得炫而无用。约束：默认视图只显示当前场景需要的频带（调音：50–1500 Hz；轴承：0–5 kHz 对数轴），全频带视图收进"专业模式"。

**原则 2：瀑布图是主角，瞬时谱是配角**
人眼对时间维度上的模式（边带等距条纹、模态衰减拖尾、音高滑动轨迹）远比对单帧曲线敏感。主视图 = WebGL 瀑布图（频率横轴 × 时间纵轴 × 颜色幅度，Viridis 色图保证色盲友好 + 幅度感知线性），瞬时谱作为顶部 20% 高度的伴随曲线。实现：单张滚动纹理 + shader 上色，每帧只上传一行新数据，确保 60 fps 下 CPU 占用可忽略。

**原则 3：从"图"到"话"——诊断结论用人话，证据图一键展开**
小白用户看不懂频谱。每个场景输出三层信息：

1. **结论卡**：「E2 弦偏低 14 音分 ↑ 拧紧」/「该杯子的敲击声特征与完好样本一致（置信度高）」
2. **证据摘要**：标注了关键峰的缩略频谱，异常处高亮
3. **专业视图**：完整瀑布图 + 数值表，供进阶用户和反馈纠错

**原则 4：测量是一个"仪式"，用引导流程保证数据质量**
诊断类场景（敲击/轴承）的最大误差来源是用户操作（手持位置、敲击力度、距离）。用分步向导：示意动画（"用指节敲杯口边缘，杯子放桌面勿手握"）→ 实时质量灯（SNR 够不够、是否削波、是否检测到敲击）→ 自动采集 3–5 次 → 出报告。**削波检测和"太吵了"提示是一等公民**，劣质输入直接拒绝出结论而不是出一个错误结论。

**原则 5：动效服务于物理直觉**
调音指针用临界阻尼弹簧动画逼近目标（不过冲、不抖动）；音准进入 ±3 音分时颜色渐变 + 触觉反馈（`navigator.vibrate`，iOS 不支持则视觉替代）。瀑布图暂停/捏合缩放/长按读数，像看地图一样看声音。

**原则 6：暗色为默认**
频谱类可视化在暗底上动态范围表现最好，且使用场景常在室内/舞台。提供亮色模式但不优先打磨。

## 6. 声音指纹库的众包采集机制

裂纹/轴承场景没有公开数据集，指纹库是本项目长期护城河。但**全端侧 + 隐私优先**与"众包上传"存在张力，机制设计如下：

### 6.1 上传的不是音频，是特征向量

默认情况下**任何原始音频都不离开设备**。用户选择贡献时，上传的是端侧提取的脱敏特征包（~2 KB JSON）：

```jsonc
{
  "schema": "fingerprint/v1",
  "scenario": "tap-test",
  "object": { "type": "ceramic-mug", "material": "porcelain", "sizeHint": "300ml" },
  "label": { "condition": "cracked", "verifiedBy": "visual", "confidence": "user" },
  "features": {
    "modalPeaks": [{ "f": 1832.4, "zeta": 0.011, "amp": -23.1 }, ...],
    "spectralCentroid": 2241.0, "decayT20": 0.41, "crestFactor": 6.2
  },
  "device": { "model": "Pixel 8", "os": "Android 15", "ua": "..." },  // 用于频响归一化
  "quality": { "snr": 31.2, "clipped": false, "hits": 5 }
}
```

可选勾选"附带 1 秒原始敲击片段"（用于未来改进特征提取），明确告知、默认不勾。

### 6.2 标签真值策略（众包最难的部分）

- **强真值优先**：引导用户贡献"前后对"——例如杯子摔裂前你测过、裂后再测一次；新轴承 vs 用了三年的同型号。前后对样本权重 ×5。
- **可见验证**：裂纹类要求用户选择验证方式（肉眼可见裂纹 / 漏水确认 / 仅怀疑），"仅怀疑"样本只进观察池不进训练池。
- **设备多样性即特征**：同一物体不同手机的录音差异，正是训练频响鲁棒模型的素材，机型字段必填。

### 6.3 激励与冷启动

1. **自建种子库（第一优先级，不依赖众包）**：自己花两周采集 200+ 样本——二手市场买 20 个杯/碗/瓷砖，逐个敲击建档后人为致裂再敲（成本 <500 元，是本项目唯一接近"硬件"的开销，仍属耗材）；风扇数据用旧电脑风扇 + 人为注入缺陷（剪一角叶片、轴承进灰）。
2. **游戏化**：「敲一敲挑战」——盲测模式让用户猜完好/有裂，App 出判断，双方对答案，结果可生成分享卡片（传播抓手）。
3. **贡献者可见回报**：贡献样本的用户解锁"我的物品声纹档案"——同一物品的历史声纹时间线（杯子的"体检记录"），数据反而留在本地，云端只有匿名特征。
4. **透明度**：公开指纹库统计页（多少样本、覆盖哪些机型/物品），并承诺特征库以 CC 协议开放下载——吸引学术/极客社区贡献，也是免费 PR。

### 6.4 后端最小化

接收端只需一个无状态函数（Cloudflare Worker / Vercel Function）做 schema 校验 + 写入对象存储，无账号体系，用一次性匿名 ID 防滥用（限流）。审核流水线：人工抽审 + 自动质量分（SNR、特征完整性）。**月成本目标 <$5。**

## 7. 里程碑（4 阶段）

### Phase 1：底座 + 可玩的频谱仪（2 周）

- 交付物：
  - PWA 骨架（离线可用、可安装），COOP/COEP 配置完成
  - 采集管线：AudioWorklet → SAB 环形缓冲 → Worker，三大音效处理确认关闭（含 getSettings 回读）
  - JS FFT + Welch + 峰插值，配 Python 对照测试
  - WebGL 瀑布图 60 fps（中端安卓实测），捏合缩放、暂停、长按读数
- **验证标准**：播放 1 kHz 标准音，谱峰读数误差 <0.5 Hz；连续运行 10 分钟无丢帧/内存增长；iPhone Safari + 安卓 Chrome 双端可用。

### Phase 2：调音器 + 琴颈诊断 MVP 上线（3 周）

- 交付物：
  - YIN 基频估计 + 指针 UI，E2–E4 全弦覆盖
  - 不谐和度分析 + 12 品引导流程 + 诊断报告卡（Beta 标签）
  - 麦克风健康自检向导；分享卡片生成
  - 上线到公开域名，埋点（端侧聚合的匿名使用统计）
- **验证标准**：与 Peterson/BOSS TU 类调音器对比，±2 音分内一致率 >95%（自测 3 把琴 × 2 部手机）；5 位真实吉他用户完成完整调音流程无求助；Lighthouse PWA 满分。

### Phase 3：敲击验裂纹「实验室」（3 周）

- 交付物：
  - 自建种子库 v1（≥200 条标注样本，含 ≥30 个前后对）
  - 瞬态截取 + 模态提取（频率/阻尼/分裂检测）管线；WASM FFT 后端接入并通过基准测试
  - 引导式敲击流程 + 三层结论 UI；指纹特征上传链路（含隐私同意流）
  - 「敲一敲挑战」盲测模式
- **验证标准**：种子库留出集上，裂纹二分类查准/查全均 >80%（杯碗瓷砖三类）；阻尼比估计与 Python 参考实现误差 <5%；至少 50 条外部众包样本入库。

### Phase 4：旋转机械诊断 + 指纹库飞轮（3 周）

- 交付物：
  - 长时采集模式 + 倒谱/包络谱分析；风扇健康报告（转速估计、边带/冲击指标、趋势对比）
  - "物品档案"：本地历史声纹时间线 + 复测对比
  - 指纹库公开统计页 + 特征数据集首次开放发布
  - 机型频响补偿表 v1（≥10 款主流机型）
- **验证标准**：对人为致损风扇样本，好/坏判别准确率 >85%；同一风扇隔天复测指标漂移 <10%；完成一篇技术博客（拉新内容）。

## 8. 主要风险与对策

| #   | 风险                                                                                                                                              | 影响                                     | 对策                                                                                                                                                                                                                                                                                                                                                             |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **手机麦克风频响差异**：各机型频响曲线天差地别（尤其 <100 Hz 滚降和 >8 kHz），同一物体在不同手机上特征不可比；MEMS 麦克风个体差异叠加机壳声学影响 | 跨设备指纹匹配失效，诊断类场景准确率坍塌 | ① **算法层优先用频响不敏感特征**：频率位置（模态频率、边带间隔、基频）对频响几乎免疫，幅度敏感特征（质心、能量比）降权或仅做同设备纵向对比；② 机型频响补偿表：众包数据按机型聚类反推相对频响 + 参考已公开测量数据；③ 自校准向导：用手机扬声器播扫频、另一部手机录（双机用户），或引导用户用同一设备做"前后对"对比而非绝对判断；④ UI 明示置信度随设备数据多寡变化 |
| 2   | **浏览器音频处理链不可控**：部分机型忽略 `echoCancellation:false` 等 constraints，或系统层强制 AGC；iOS AudioContext 挂起策略多变                 | 输入信号被偷偷"美化"，幅度/瞬态特征失真  | `getSettings()` 回读 + 启动时自检（播放已知信号检测 AGC 行为）；检测到不可关闭的处理时降级到频率类特征并明示；维护机型行为兼容表（众包字段已含 UA）；iOS 上每个交互入口都做 `audioContext.resume()` 防御                                                                                                                                                         |
| 3   | **诊断类场景的"伪科学"信任危机**：裂纹/轴承判断本质是统计推断，误报一次（说好杯是裂的）就会被截图群嘲                                             | 口碑反噬，产品被定性为玩具               | 结论永远带置信度与证据图，低置信时输出"无法判断，建议补测"而非硬猜；MVP 先上可硬验证的调音建立信任；盲测挑战模式把"会出错"转化为游戏性；免责声明 + 不进入安全攸关场景（不做"燃气管道检漏"这类宣传）                                                                                                                                                              |
| 4   | **指纹库冷启动失败**：众包无人贡献，长尾物品永远没数据                                                                                            | 裂纹场景只能覆盖种子库内的杯碗瓷砖       | 种子库自采 200+ 条保底（Phase 3 验收线不依赖众包）；产品定位上"同物前后对比"模式不需要库（自己跟自己比），作为无库时的默认能力；数据集开放吸引社区；物品类型按需扩展（用户搜索什么物品测不了 → 下一批采集清单）                                                                                                                                                  |
| 5   | **单人项目范围失控**：三个场景 × DSP × 可视化 × PWA，每个都能吃掉数月                                                                             | 烂尾                                     | 严格按里程碑串行，每阶段有可上线交付物；"不做清单"写进本文档；算法先 Python 验证再移植，避免在 TS 里调研；WASM 等优化推迟到有基准数据证明必要                                                                                                                                                                                                                    |
| 6   | **环境噪声与混响**：家庭环境 40–60 dB 底噪，敲击的高阶模态、轴承边带可能被淹没                                                                    | 真实环境准确率远低于安静环境             | 实时 SNR 质量灯，不达标拒绝出结论；引导用户靠近测量（轴承场景麦克风贴近 5 cm）；多次测量聚合；Welch 长时平均换 SNR（轴承场景天然允许长录音）                                                                                                                                                                                                                     |
