# 项目 10：「可证伪的养生」个人 N-of-1 实验平台

> 把随机对照试验的科学方法搬进日常生活：对自己做单被试实验，用数据回答"这个养生习惯对**我**有用吗"。隐私优先，健康数据全部端侧处理，可单人开发执行。

---

## 1. 一句话定位与目标用户

**一句话定位**：一个帮你对自己做"单被试随机对照试验（N-of-1 trial）"的工具——自动设计实验方案（区组随机化、盲法、washout 期）、自动从手环/手表拉取客观数据，最后用贝叶斯统计告诉你："下午咖啡使你的入睡延迟 +23 分钟，95% 可信区间 [11, 36]，效应为正的概率 99.2%"。

**目标用户**（按优先级）：

| 优先级 | 人群画像                          | 特征                                                                                     | 为什么是他们                                              |
| ------ | --------------------------------- | ---------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| P0     | 量化自我（Quantified Self）爱好者 | 已有 Apple Watch / Oura / 小米手环，看过自己的睡眠曲线，对"褪黑素到底有没有用"有真实困惑 | 数据接入零教育成本，依从性最高，愿意忍受 4-6 周的实验周期 |
| P1     | 理性消费的保健品购买者            | 每月在褪黑素、镁、益生菌上花几百块，但心里嘀咕"是不是安慰剂"                             | 有明确的"省钱/止损"动机，实验结论直接指导消费决策         |
| P2     | 循证医学/统计学背景的专业人士     | 医生、数据科学家、研究生                                                                 | 早期口碑传播者，会挑剔方法学——这反而是产品壁垒的检验者    |

**反目标用户**：寻求诊断或治疗方案的患者、想测试处方药的用户（见第 6 节合规红线）、期待"3 天出结论"的用户。

**核心价值主张**："可证伪"是卖点而非负担——市面上所有养生 App 都在告诉你"该做什么"，只有我们帮你证明"什么对你没用"，让你理直气壮地停掉无效的习惯和开销。

## 2. MVP 范围

### 2.1 实验模板选择：咖啡因 × 睡眠是最佳起点吗？

**结论：是，但应与"褪黑素 × 睡眠"并列为双模板上线。** 理由如下：

**咖啡因 × 睡眠作为模板一（推荐为默认）**：

1. **干预可逆且日粒度**：咖啡因半衰期约 5 小时（个体差异 3-7 小时），单日干预、当晚见效、次日基本洗脱（washout 只需 1 天），实验周期可压缩到 3-4 周，是所有候选实验里**周期最短的**——MVP 阶段用户留存的最大敌人是实验太长。
2. **结局指标客观且手环可测**：入睡延迟（sleep onset latency）、总睡眠时长、深睡比例、静息心率/HRV，全部能从 HealthKit / Health Connect 读到，**不依赖主观日记**，数据质量天然高。
3. **效应量大，统计功效友好**：文献中下午咖啡因对入睡延迟的影响在 10-40 分钟量级，相对睡眠数据夜间噪声（SD 约 15-25 分钟）效应量 d≈0.5-1.0，**20-28 个观测日就能得到有意义的可信区间**——这意味着 MVP 用户能在一个月内拿到"哇"时刻。
4. **零成本、零安全顾虑**：不需要购买任何东西（喝/不喝下午的咖啡），不涉及补剂摄入的法律和安全灰区，合规上最干净。
5. **天然适合"剥夺式"设计**：干预是"下午 2 点后不摄入咖啡因" vs "正常喝"，依从性记录简单（一个打卡按钮）。

**咖啡因模板的弱点（必须诚实面对）**：**无法做到盲法**——你知道自己今天喝没喝咖啡。这是开放标签（open-label）实验，期望效应会污染主观指标。对策：MVP 中咖啡因实验**只用客观手环指标做主分析**，主观感受仅作次要指标并在报告中明确标注"未设盲，仅供参考"。

**褪黑素 × 睡眠作为模板二（体现产品完整方法学）**：

1. **可以真正设盲**：引导用户（或其同住者）准备褪黑素 + 外观相近的安慰剂（维生素 C 片/淀粉空胶囊），编号装入每日药盒，由 App 持有随机序列、实验结束才揭盲——这是产品"盲法提醒"能力的展示位，咖啡因模板展示不了。
2. **直击付费痛点**：褪黑素是日本和中国市场销量最高的助眠补剂之一，"它对我到底有没有用"是真金白银的问题。
3. **同样是日粒度干预、手环可测结局**，可复用咖啡因模板 90% 的工程实现。
4. 弱点：需要用户自备安慰剂（操作门槛），且褪黑素有处方/非处方地区差异（日本为"机能性表示食品"灰区，需在免责声明中处理，见第 6 节）。

**为什么不选其他候选**：

- 冷水澡/运动 × 情绪：结局主观、无法盲法、效应小。
- 镁/益生菌 × 任何指标：起效慢（数周），washout 长达 1-2 周，单次实验要 3 个月以上，MVP 阶段必死。
- 屏幕时间 × 睡眠：干预依从性极差（戒手机比戒咖啡难）。

### 2.2 MVP 功能边界

**做（In Scope）**：

- 2 个实验模板（咖啡因×睡眠、褪黑素×睡眠），每个模板内含预设的随机化方案、washout 规则、结局指标、先验分布
- 实验设计向导：3 步问答（你想测什么 → 你的基线情况 → 确认方案），自动生成日历化的实验计划
- 每日打卡：今日分组提醒（"今天是 B 日：下午 2 点后请勿摄入咖啡因"）、依从性确认（做到了/没做到/部分做到）
- Apple HealthKit 睡眠数据自动接入（iOS 先行，理由见第 4 节）+ 手动记录兜底
- 贝叶斯分析报告：效应点估计 + 95% 可信区间 + 方向概率 + 通俗解读 + 完整方法学附录
- 端侧计算与存储：所有健康数据和分析结果不出设备

**不做（Out of Scope，v1.1+）**：

- 自定义实验设计器（自由选干预/结局）——方法学坑太多，模板先行
- Google Health Connect / Fitbit / Oura 直连
- 多人实验、社区分享原始数据
- 贝叶斯层次模型跨用户借力（borrowing strength）——涉及数据上传，与隐私承诺冲突，需先设计联邦方案
- AI 解读聊天

### 2.3 形态

**iOS App（SwiftUI）**而非 Web App。决定性理由：HealthKit 只能由原生 App 访问，而自动数据接入是本产品相对"Excel 自记录"的核心增量（详见第 4 节）。Web 仅做营销落地页 + 方法学博客。

## 3. 实验设计引擎

### 3.1 N-of-1 方法学内核

N-of-1 试验 = 单被试、多周期交叉（multiple-period crossover）随机对照试验。被试既是处理组也是对照组，消除了个体间差异，回答的是"对这个人"而非"对平均人"的因果问题。引擎需固化以下方法学要素：

**(a) 区组随机化（Block Randomization）**

- 以"区组对（pair）"为随机化单元：每个区组包含 1 个 A（对照）日簇和 1 个 B（干预）日簇，区组内顺序随机（AB 或 BA），保证 A/B 数量严格平衡且分布在整个实验期，抵御时间趋势混杂（工作日/周末、月经周期、季节、压力波动）。
- 咖啡因模板默认：**簇长 2 天 × 6 个区组 = 24 天**（簇长 2 而非 1，是为了缓冲"前一晚没睡好导致今天更想喝咖啡"的 carryover-into-behavior 效应，并减少每日切换的依从负担）。
- 约束随机化：禁止超过 2 个同类簇连续出现（即最长连续同条件 4 天），防止用户从模式中"猜出"分组（对盲法实验尤其重要）。
- 随机种子由设备安全随机数生成，盲法实验中序列加密存储、UI 不可见，揭盲操作不可逆且记录时间戳。

**(b) Washout 期**

- 规则引擎按"干预药代/生理动力学"参数化：每个模板定义 `washoutDays`（条件切换日之间的排除天数）和 `excludeFromAnalysis`（washout 期数据是否纳入）。
- 咖啡因：washout = 0 天（半衰期短，当日条件只影响当晚），但**每个条件簇的第 1 晚标记为"过渡夜"，主分析默认剔除**，敏感性分析中纳入。
- 褪黑素：washout = 1 天（外源性褪黑素半衰期约 40-60 分钟，但对昼夜节律相位可能有 1-2 天残留影响），簇长 3 天 × 5 区组 + 切换日剔除 = 约 5 周。
- 实验开始前强制 **5-7 天基线期**：不做任何干预，只收数据。用途：① 估计该用户结局指标的均值和方差，用于个体化功效预估和先验设定；② 检测数据质量（手环佩戴率 <70% 则提示先解决佩戴习惯）。

**(c) 盲法提醒系统**

- 开放标签模板（咖啡因）：每日早 8 点推送当日条件 +下午 1:30 二次提醒（B 日"最后一杯窗口即将关闭"）。
- 盲法模板（褪黑素）：引导期向导教用户制作编号药盒（自己装或请同住者装，App 给出逐步图文指引：14 个信封、按 App 显示的编号顺序装入），每晚推送只说"今晚服用 X 号"，从不透露 X 号是什么。揭盲仅在以下条件之一满足时允许：实验完成 / 用户主动中止并确认 / 报告不良反应。
- **破盲登记**：每个区组结束时问一道题——"你猜这几天吃的是真药还是安慰剂？（真/假/猜不出）+ 信心 1-5"。实验结束计算盲法完整性指数（James/Bang index 简化版），写入报告：如果用户猜对率显著高于随机，报告自动降级结论可信度并说明原因。这是把"破盲"从隐藏缺陷变为被测量的变量（见第 8 节风险 R1）。

**(d) 依从性记录**

- 每日一次轻交互：「今天的方案你执行了吗？」三态按钮（完全执行 / 部分执行 / 未执行）+ 可选备注（"下午朋友请喝了奶茶"）。
- 依从性数据进入分析的两条路径：① 主分析按 ITT（意向性分析）原则用分配的条件；② 敏感性分析做 per-protocol（剔除未依从日）。两者结论不一致时报告明确提示。
- 漏打卡 >2 天自动推送挽回提醒；区组依从率 <50% 时引擎建议作废该区组并顺延补一个区组（最多顺延 2 个，防止实验无限拖长）。

**(e) 方案自动生成流程**

```
用户选模板
  → 问答采集参数（咖啡因日常摄入量、平时就寝时间、手环型号、可投入周数）
  → 引擎校验适格性（如"你平时不喝咖啡"→ 咖啡因剥夺实验无意义，劝退或转介绍）
  → 用基线方差 + 模板效应量先验 跑功效模拟（蒙特卡洛 1000 次，端侧 <1s）
  → 输出："24 天方案，若真实效应 ≥15 分钟，你有约 85% 概率得到确定性结论"
  → 用户确认 → 生成加密随机序列 + 写入日历化计划 + 注册本地推送
```

方案对象（JSON）包含：随机序列（盲法实验加密）、每日条件、washout 标记、提醒时刻表、预注册的主结局/次结局/分析模型——**"预注册"在 UI 上明确呈现**：方案一旦开始，主结局和模型不可更改，这既是科学性也是产品叙事（"我们不让你事后挑数据"）。

## 4. 数据接入方案

### 4.1 优先级与现实难度评估

| 渠道                               | 优先级                   | 现实难度    | 说明                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------------------------- | ------------------------ | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Apple HealthKit (iOS)              | **P0，MVP 唯一自动渠道** | ★★☆☆☆ 低-中 | API 成熟稳定；`HKCategoryTypeIdentifier.sleepAnalysis` 可读分期睡眠（Apple Watch 原生写入，Oura/Garmin/Fitbit/华米也都桥接写入 HealthKit——**接一个 HealthKit 等于间接接入了几乎所有主流设备**）；数据天然在端侧，与隐私架构完美契合。难点：不同来源写入格式不一（有的只有 inBed/asleep，有的有分期），需要写一层"睡眠会话重建"逻辑（合并碎片、去重多来源、计算入睡延迟）；App Review 对 HealthKit 用途说明审查较严，需准备清晰文案。 |

| Google Health Connect (Android)    | **P1，v1.1**             | ★★★☆☆ 中    | API 2023 年后趋于稳定，`SleepSessionRecord` 含分期；但 Android 设备/ROM 碎片化导致后台读取可靠性参差，且日本目标市场 iPhone 份额约 60-70%，iOS 先行是正确的市场顺序。预留：数据层从第一天起定义平台无关的 `SleepSession` 领域模型，HealthKit 只是其中一个 adapter。                                                                                                                                                                  |
| Oura / Fitbit / Garmin 云 API 直连 | P2，大概率永远不做       | ★★★★☆ 高    | 需要 OAuth + 服务器中转 token + 数据经云——**直接违反端侧隐私承诺**；且各家审核/配额/商务条款繁琐。既然它们都能写 HealthKit/Health Connect，直连的边际价值很低。                                                                                                                                                                                                                                                                      |

### 4.2 关键工程决策

- **入睡延迟的计算**：HealthKit 中没有现成的 "sleep onset latency" 字段。算法：取当晚最早的 `inBed` 记录起点（无 inBed 记录则用用户设定的就寝提醒时刻或手动记录的就寝时刻）到第一个 `asleep*` 区间起点的间隔。该算法的局限（躺床玩手机会被算进延迟）在报告方法学附录中如实披露。
- **多来源冲突**：用户同时有 Apple Watch 和 Oura 时，按用户指定的首选来源取数，绝不混合平均。
- **数据缺失策略**：缺失夜标记为 missing 而非插补（贝叶斯模型天然处理不平衡数据）；连续缺失 ≥3 天触发"手环没戴？"提醒。
- **隐私落点**：健康数据仅存于 App 沙盒（SQLite/GRDB，启用 iOS Data Protection），不进任何自建服务器；iCloud 备份默认排除健康原始数据（仅备份实验方案与去标识的分析摘要，且提供开关）；分析全部本地执行（见第 5 节）。

## 5. 统计分析方案

### 5.1 模型选型：分层推进，不要一步到位

**结论：MVP 用"正态共轭先验的贝叶斯两条件均值差模型"解析解起步，v1.x 升级为端侧 MCMC 的单用户贝叶斯回归；跨用户层次模型在隐私方案成熟前不做。**

**第 0 层（不采用）：频率学派 t 检验。** 为什么连"起步"都不用它：① p 值无法表达产品的核心句式"咖啡使你延迟 +23 分钟 [11, 36]"——可信区间的直觉解读（"真值有 95% 概率在此区间"）正是置信区间不具备的；② N-of-1 样本小，p>0.05 时 t 检验只能说"没发现"，而贝叶斯可以说"效应大于 10 分钟的概率仅 8%，基本可排除有意义的影响"——**对"证伪养生"这个定位，量化的无效结论是核心交付物**；③ t 检验也省不了多少工程量。

**第 1 层（MVP 主分析）：共轭正态模型，解析解。**

- 模型：对结局 Y（如入睡延迟，分钟），A 日 Y~N(μ_A, σ²)，B 日 Y~N(μ_B, σ²)，关注 δ = μ_B − μ_A。
- 先验：μ 用基线期数据定中心的弱信息正态先验；δ 的先验 N(0, τ²)，τ 按模板设定（咖啡因模板 τ=30 分钟——"效应超过 ±60 分钟先验上不太可能"），σ² 用 Inverse-Gamma 共轭先验由基线方差锚定。
- 后验：Normal-Inverse-Gamma 共轭，**纯解析解，闭式公式，端侧 Swift 几毫秒算完**，无任何数值计算依赖。
- 输出：δ 的后验均值、95% 可信区间、P(δ>0)、P(|δ|>最小有意义效应 MID)（咖啡因模板 MID 预设 15 分钟，用户可调）。
- 已知妥协（在方法学附录中披露）：忽略夜间数据的自相关与时间趋势；用"剔除过渡夜 + 区组平衡随机化"在设计端而非模型端控制这些偏倚。对 MVP 的两个短周期模板，这个妥协是可接受的。

**第 2 层（v1.x 主分析）：单用户贝叶斯回归，端侧 MCMC。**

- 模型扩展：Y_t = α + δ·B_t + β₁·weekend_t + β₂·t（线性时间趋势）+ ε_t，可选 AR(1) 残差。
- **端侧可行性结论：完全可行，且不需要 WASM。** 原生 iOS App 直接用 Swift 实现 NUTS/HMC（或移植 [Stan math 的核心采样器] 量级的代码，参数维度 ≤6）：4 链 × 2000 迭代在 iPhone 12 以上约 1-3 秒。备选捷径：变分推断或 Laplace 近似（牛顿法找 MAP + Hessian 求曲率），毫秒级，对这种低维近高斯后验精度足够。
- WASM 路线（仅当未来做 Web 版才相关）：编译 Stan→WASM 不现实（依赖重），现实选项是手写 JS/Rust→WASM 的 NUTS，或用 TensorFlow.js Probability。结论：**WASM 跑低维 MCMC 技术上可行（秒级），但 MVP 选了原生 App，此问题暂不存在**——记录于此防止未来重复调研。
- 模型校验：每次分析自动跑后验预测检查（PPC），把模拟数据与实际数据的分布叠图放进报告附录。

**第 3 层（远期，需联邦/差分隐私方案）：跨用户层次模型。** 用人群后验做新用户的先验，缩短实验周期。价值大但与"数据不出设备"冲突，仅当设计出"只上传后验摘要统计 + 差分隐私噪声"的方案后再启动，MVP 阶段明确不做。

### 5.2 报告设计（产品的"啊哈"时刻）

- 首屏一句话：「下午咖啡使你的入睡延迟 **+23 分钟**（95% 可信区间 [11, 36]）。效应为正的概率 99.2%。」配后验分布密度图（MID 阈值竖线标出）。
- 第二屏行动建议（严守合规边界，见第 6 节）：只陈述统计事实 + 通用生活习惯信息，不给医疗建议。
- 第三屏诚实度面板：依从率、缺失天数、破盲指数、ITT vs per-protocol 是否一致、本实验的局限清单。**诚实度面板是品牌，不是附录。**
- 可分享卡片：仅含结论与区间，不含原始数据，用户显式确认后才生成。

## 6. 医疗合规红线

> 原则：本产品是"个人生活方式自我观察工具 + 统计计算器"，**不是医疗器械、不提供诊断/治疗/预防疾病的功能**。所有设计决策向这条定位收敛。

**红线清单（硬性，写入产品需求且代码层面强制）**：

1. **不宣称诊断/治疗**：全部文案禁用"治疗""改善失眠（症）""诊断""疗效"等词；用"观察""与……的关联（在你身上）""个人实验"。建立禁用词表，文案上线前过 lint。报告结论句式固定为统计陈述，永不输出"你应该服用/停用 X"。
2. **处方药与疾病情境劝阻**：实验创建流程含筛查问题——若用户表示想测试处方药、正在治疗中的疾病相关干预、或提及失眠症/抑郁等诊断，**硬阻断**该实验创建并显示："涉及药物或疾病的任何调整请咨询医生。本工具仅适用于咖啡、非处方补剂等日常生活习惯。" 模板库永不收录处方药模板。自定义实验上线后（v1.1+）维护处方药关键词黑名单。
3. **不良反应逃生门**：实验进行中常驻"我感觉不适"入口 → 立即建议停止实验 + 提示就医 + 允许即刻揭盲。不提供任何症状评估。
4. **年龄与脆弱人群**：服务条款限 18 岁以上；onboarding 声明孕期、哺乳期、确诊睡眠障碍者不适用。
5. **免责声明设计**（分层而非一次性弹窗）：
   - onboarding 一次性确认页（需滚动到底 + 显式勾选）："本应用不提供医疗建议……"
   - 每份报告底部固定声明 + 报告首屏角标「个人观察，非医学结论」
   - 褪黑素模板入口处的地区化提示（日本：褪黑素非药品流通的现状与购买合规提醒；不同地区法规差异声明）
6. **监管定位自查**：对照日本药机法（医疗机器该当性）与美国 FDA General Wellness 指南——产品只涉及"一般健康维持"，不针对疾病，属于豁免范畴；**但一旦未来加入"失眠改善"类宣传或疾病相关模板，性质即改变**。把这条写进产品决策 checklist：每个新模板上线前过一遍"是否触及疾病/药品"评审。
7. **隐私即合规**：端侧处理使产品基本避开 GDPR/APPI 健康特殊类别数据的服务器侧义务；但仍需隐私政策明确说明 HealthKit 数据用途、不出设备、不用于广告（这也是 Apple HealthKit 审核的硬性要求——HealthKit 数据禁止用于广告/数据挖掘，违者下架）。

## 7. 里程碑（4 阶段）

### 阶段 1：方法学内核 + 数据通路（第 1-3 周）

**交付物（可验证）**：

- Swift Package：`ExperimentEngine`（随机化、washout、方案生成）+ `BayesCore`（共轭后验解析解），**单元测试覆盖：随机化平衡性统计检验、后验公式与 R/PyMC 参考实现对照误差 <1e-6**
- HealthKit 睡眠读取 + 睡眠会话重建，用自己 7 晚真实数据验证入睡延迟计算与手表 App 显示一致（±5 分钟内）
- 验证方式：`swift test` 全绿 + 对照脚本输出一致

### 阶段 2：可用的咖啡因实验闭环（第 4-7 周）

**交付物**：

- iOS App 内测版（TestFlight）：模板向导 → 24 天方案 → 每日推送与打卡 → 自动取数 → 报告页
- **自己作为 0 号被试完整跑完一轮咖啡因实验**（这同时是产品验证和最好的营销素材）
- 验证方式：0 号实验产出一份完整报告；3 位 QS 爱好者装机并完成基线周

### 阶段 3：盲法模板 + 报告打磨（第 8-12 周）

**交付物**：

- 褪黑素盲法模板（药盒指引、加密序列、破盲登记、揭盲流程）
- 报告 v2：诚实度面板、PPC 图、分享卡片；合规审查（禁用词 lint、免责声明全链路）
- 验证方式：5-10 位内测用户至少 3 人完成完整实验；破盲登记数据可计算盲法指数；模拟 App Review 自查清单通过

### 阶段 4：公开发布（第 13-16 周）

**交付物**：

- App Store 上架（准备 HealthKit 用途说明与隐私营养标签）；落地页 + 方法学白皮书（公开随机化与统计方法全部细节——"可证伪"也适用于产品自身）
- 指标基线：30 天内 ≥50 个实验启动、≥40% 实验完成率（行业常识：能到 40% 即健康）
- 验证方式：上架成功；埋点（端侧聚合、匿名）看完成漏斗

## 9. 第一周行动清单

> 前提：solo 开发者，全职投入。本周目标 = 方法学决策全部落纸 + 核心引擎可测试 + 数据通路打通验证。

**Day 1（周一）：方法学定稿日**

- 上午：写定咖啡因模板规格书 v1：干预定义（下午 2 点后咖啡因 0mg vs 正常摄入）、主结局（入睡延迟）、次结局（总时长、HRV、晨起精力）、簇长 2×6 区组、过渡夜剔除规则、MID=15 分钟
- 下午：写定统计规格书 v1：Normal-Inverse-Gamma 共轭模型的完整公式推导（手写推一遍，不抄）、先验参数表、输出指标定义（后验均值/CrI/P(δ>0)/P(|δ|>MID)）
- 产出：两份 markdown 规格书，作为后续所有代码的"预注册协议"

**Day 2（周二）：统计内核实现日**

- 用 PyMC（或 R brms）写参考实现：模拟数据 → 共轭解析解 vs MCMC 后验对照，确认公式推导无误
- Swift 实现 `BayesCore`：共轭后验闭式解 + 蒙特卡洛功效模拟；单测对照 Day 2 上午的参考值（误差 <1e-6）
- 产出：`BayesCore` Swift Package，`swift test` 全绿

**Day 3（周三）：实验引擎实现日**

- Swift 实现 `ExperimentEngine`：约束区组随机化（含"不超过 2 个连续同类簇"约束）、方案 JSON 生成、日历展开、washout/过渡夜标记
- 单测：生成 10000 个序列，统计检验 A/B 平衡性与约束满足率 100%
- 产出：`ExperimentEngine` Package + 测试全绿

**Day 4（周四）：HealthKit 通路日**

- 建 iOS App 壳工程（SwiftUI），申请 HealthKit entitlement，实现睡眠数据读取授权流程
