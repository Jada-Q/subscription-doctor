# 项目 6：浏览器端的「合同 X 光机」

> Contract X-Ray（契約レントゲン）— 隐私优先的合同风险扫描器。技术哲学与 Subscription Doctor 完全一致：**WASM + 端侧推理 + 规则库，数据永不离开设备**。本计划假设单人执行，复用 `/home/user/subscription-doctor` 已验证的管线（PaddleOCR ONNX WASM → 解析 → 规则匹配 → 评分报告）。

---

## 1. 一句话定位与目标用户

**一句话定位**：上传租房合同照片/PDF，30 秒内在浏览器本地标出风险条款（敷金不返还、过高违约金、自动续约、单方面变更权等），生成"合同体检报告"——非法律意见，但让你知道该问什么。

**MVP 聚焦合同类型：日本租房合同（賃貸借契約書）。** 选它的理由：

- **结构高度标准化**：日本租房合同绝大多数基于国交省「賃貸住宅標準契約書」或各大管理公司模板，条款措辞收敛，规则引擎命中率可预期（与信用卡账单格式收敛的逻辑相同）。
- **风险条款有明确法律锚点**：消費者契約法 8/9/10 条、借地借家法、国交省「原状回復をめぐるトラブルとガイドライン」、判例（更新料、敷引、退去清扫费）——规则可以引用公开权威来源，而非主观判断。
- **用户痛点强且时点明确**：搬家季（1-3 月、9-10 月）签约前 24-48 小时内是刚需窗口，与 Subscription Doctor 的"账单到手时刻"类似，传播叙事清晰（「ハンコを押す前に 30 秒スキャン」）。
- 保险条款页数太多（几十页 OCR 体验差）、用户协议无付费痛点，均放到 v2。

**目标用户**：20-35 岁日本租房者，尤其首次独居/搬家的年轻人；隐私敏感（合同含姓名住址年收，绝不愿上传云端——这正是端侧处理的卖点而非妥协）。

## 2. MVP 范围

**做（In Scope）**

1. 输入：合同照片（多页，复用多卡上传 UX）+ 文本型 PDF（pdf.js 直接抽文本，跳过 OCR）。
2. 本地 OCR：复用 PaddleOCR v5 mobile（中日文字典已覆盖日文），逐页识别。
3. 条款切分器：OCR 文本 → 按「第◯条」「（◯◯）」标题、全角数字编号切分为条款单元（clause units）。
4. 规则引擎：约 40 条租房风险规则（见 §4），输出命中条款 + 风险等级（赤/黄/青）+ 法律锚点 + 「不動産屋に聞くべき質問」话术。
5. 体检报告：风险评分 0-100 + 条款高亮列表 + 分享卡（复用 share card，分享卡只含统计不含合同原文）。
6. 免责层：首屏与报告内嵌「法律意见ではありません」（见 §6）。
7. Demo 模式：内置一份虚构高风险合同样本，无需上传即可体验。

**不做（Out of Scope）**

- 保险条款、用户协议（v2）；云端 LLM 兜底（v1.1 可选，默认关闭）；条款改写建议/谈判代理；扫描件 PDF 的逐页渲染 OCR 之外的版面分析；账号系统/历史保存（仅 sessionStorage）。

**验收标准**：对 10 份真实模板合同（国交省标准 + 大手管理会社模板 + 含已知问题条款的样本），风险条款召回 ≥ 80%，误报每份 ≤ 2 条；iPhone Safari 实拍照片全流程 < 60 秒。

## 4. 风险条款规则库设计

### 规则结构（`lease-rules.json`，每条规则）

```jsonc
{
  "id": "lease-early-termination-penalty",
  "name": "高額な違約金（短期解約違約金）",
  "category": "penalty", // penalty | renewal | restoration | unilateral | fee | other
  "severity": "red", // red(法的に争える可能性) | yellow(要確認・交渉余地) | blue(情報提供)
  "triggers": {
    "keywords": [["違約金"], ["解約", "解除"]], // AND-of-OR 关键词组
    "patterns": ["賃料.{0,10}([2-9]|[０-９]{1,2})[ヶか箇]月分.{0,20}違約金"], // 正则（含全角）
    "threshold": { "field": "penaltyMonths", "op": ">=", "value": 2 }, // 可选数值阈值
  },
  "negativePatterns": ["違約金は発生しない"], // 抑制误报
  "legalBasis": {
    "law": "消費者契約法第9条1号",
    "source": "https://elaws.e-gov.go.jp/document?lawid=412AC0000000061",
    "note": "平均的な損害を超える違約金条項は超過部分が無効となり得る",
  },
  "explanation": "解約時に賃料2ヶ月分以上の違約金が設定されています。…", // 平易な日本語
  "questionToAsk": "この違約金の根拠（平均的な損害）を教えてもらえますか？", // 行动话术
  "scoreWeight": 15,
}
```

设计要点：每条规则必须有 `legalBasis.source`（可点击的权威出处）——这是免责设计的一部分（"我们只是指出条款 + 给出公开法条链接"）；`questionToAsk` 让产出物是"问题清单"而非"法律结论"。

### 初始覆盖（约 40 条，按类别）

- **原状回復・敷金**（~10 条）：敷金全额不返还/敷引、退去时清扫费定额负担、自然损耗修缮转嫁、鍵交換費入居者負担 等（锚点：国交省原状回復ガイドライン、消費者契約法10条）。
- **解約・違約金**（~8 条）：短期解約違約金 ≥2 个月、解約予告期間 >2 个月、中途解約禁止 等。
- **更新・自動更新**（~6 条）：更新料 ≥1 个月+地域基准、自動更新+高额更新事務手数料、定期借家伪装成普通借家 等。
- **単方面变更权**（~6 条）：贷方单方面变更賃料/規約、無催告解除、即時明け渡し 等（消費者契約法8条/10条经典案例）。
- **費用・特約**（~10 条）：消臭抗菌費等暧昧附加费、24h サポート強制加入、保証会社+連帯保証人双重要求、家賃保証更新料 等。

### 数据来源合规性

- **只用公开权威来源**：e-Gov 法令检索（法条原文）、国交省指南 PDF、消費者庁/国民生活センター公开案例、裁判所公开判例要旨。均为政府公开信息，引用合法；规则库存的是**我们自己撰写的特征与解说**，不复制受版权保护的解说书内容。
- **不收录真实用户合同**：测试样本一律自造或用国交省公开标准模板改写，避免任何个人信息入库。
- 每条规则记录 `source` + 复核日期字段（仿 cancelUrl 的"会过期"教训），法条修订时可批量复查。

## 5. 端侧 NLP 方案对比

| 方案                                                                                            | 优点                                                                                           | 缺点                                                                               | 体积/性能          |
| ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------ |
| **A. 纯规则 + 正则 + 数值阈值**                                                                 | 零额外下载；可解释（每个命中都能指到法条）；可测试（vitest 直接断言）；与现有 matcher 哲学一致 | 措辞变体覆盖有限；OCR 噪声下正则脆弱（用 normalize + 模糊间隔 `.{0,10}` 缓解）     | 0 MB，<10ms        |
| B. 端侧小模型（日文 sentence embedding 量化 ONNX，条款 → 与规则锚句做相似度）                   | 抗措辞变体；仍然完全端侧                                                                       | +25–80MB 下载（OCR 模型之外）；iOS Safari 内存风险；阈值难调、不可解释、调试成本高 | 重，单人维护负担大 |
| C. 可选云端 LLM 兜底（用户显式 opt-in，仅发送未命中条款文本，复用既有 `GEMINI_API_KEY` 预留位） | 覆盖长尾条款                                                                                   | **打破"数据不离开设备"核心承诺**；合同文本敏感度远高于账单行                       | —                  |

**推荐：MVP = 方案 A（纯规则）**，理由：租房合同措辞收敛使规则召回足够高；可解释性本身是法律免责的一部分（"基于规则 X + 法条 Y 标出"远比"模型觉得有风险"站得住）；这正是 Subscription Doctor 已验证的路线。**v1.x 路线**：先做 A 的"模糊层"（编辑距离 + 同义词表），仅当真实误漏数据证明不够时再评估 B；C 永远是显式 opt-in + 醒目二次确认 + 默认关闭，且只发送单条条款文本而非全文。

## 6. 法律免责设计（「非法律意见」如何呈现）

原则：**免责不是一行小字，而是产品语言本身**。

1. **用词层**：全站禁用「違法」「無効」断言式用词；统一为「〜の可能性があります」「専門家への相談をおすすめします」。风险等级叫「要確認度」而非「違法度」。规则的 `explanation` 写作规范写入 CONTRIBUTING（仿 rules.json 的 keyword 规范）。
2. **结构层**：每条命中输出三段式 = ①条款引用 → ②公开法条/指南链接（用户自己看原文）→ ③「聞くべき質問」。产品交付的是**问题清单**，最终判断者是用户和真人专家。
3. **UI 层**：
   - 上传前 gate：首次使用显示一次性确认「本ツールは法律意見を提供するものではありません。表示内容は一般的な情報提供であり、具体的な判断は弁護士等の専門家にご相談ください。」+ 同意按钮（记 localStorage，try-catch 静默）。
   - 报告页顶部常驻免责横幅（不可折叠）；分享卡角落固定印「※法的助言ではありません」。
   - 每条红色条款卡片底部固定一行「個別の事情により判断は異なります」。
4. **导流层**：报告底部提供官方求助渠道链接（法テラス、国民生活センター 188、自治体宅建窗口）——把"下一步找专业人士"做成产品功能，而非免责借口。
5. **合规复查**：上线前将免责文案 + 三段式样例请一位日本律师/行政書士 spot-check（单次咨询费用级别，非聘用），确认不触及弁護士法 72 条（非弁行為）边界——核心论点：仅作信息提供与公开资料指引，不做个案法律判断。

## 8. 主要风险与对策

1. **非弁行為（弁護士法 72 条）风险** — 对策：§6 全套（信息提供定位、三段式、专家 spot-check、不做个案结论）；营销文案同样审查，绝不写「契約書を診断して違法条項を判定」之类断言。**这是唯一可能直接杀死项目的风险，M3 前必须闭环。**
2. **合同照片 OCR 质量远差于账单**（小字号、多页、纵书特約、印章遮挡）— 对策：M1 先用 20 张真实手机实拍做 OCR 质量 spike，若 v5 mobile 行识别率 <85% 再评估 server 版 det 模型或引导用户"PDF 优先 + 逐页平拍"教程；条款切分器按"容忍 OCR 噪声"设计（编号锚点而非全文依赖）。
3. **误报伤害信任 / 漏报伤害用户**（标错让中介反感用户，漏掉让用户吃亏）— 对策：负向模式（negativePatterns）+ 严格基准测试集守门；红色等级只给有明确法条/判例锚点的条款，拿不准一律降黄；报告语言始终是"要確認"而非结论。
4. **范围蔓延**（保险、用户协议、英文合同、改写建议的诱惑）— 对策：MVP 锁死賃貸借契約一种；规则 schema 预留 `contractType` 字段但不实现第二类型；每个新需求先过"是否帮助签约前 30 秒决策"。
5. **规则库过期**（法律修订、判例更新，类比 cancelUrl 老化）— 对策：每条规则带 source + reviewedAt；季度复查 checklist 写入文档；法改信息源订阅（消費者庁/国交省 RSS）。
6. **iOS Safari 内存/性能**（多页合同 > 多张账单）— 对策：沿用 1600px + numThreads=1，逐页串行 OCR + 进度条 + 页间释放 tensor；M1 即在真机用 10 页合同压测。

## 9. 第一周行动清单（M1，具体到天）

- **Day 1（周一）**：搭骨架。新建 `src/features/contract-xray/`（index.ts / page 组件 / lib / data，按 feature module 约定）；接入 TabNavigator（inline style，不用 next/dynamic）；收集语料：下载国交省「賃貸住宅標準契約書」+ 自造 2 份含问题特約的合同 PDF，打印后手机实拍 20 张（含歪斜/阴影）。
- **Day 2（周二）**：OCR spike。复用 `src/lib/ocr/engine.ts` 跑 20 张实拍图，记录逐行识别质量；做出 go/no-go 判断（行识别率 ≥85% → 继续；否则当天评估 det server 模型）；引入 pdf.js，写 `src/lib/pdf/extract.ts`（文本型 PDF 直抽）+ 测试。
- **Day 3（周三）**：条款切分器 v1。`segment.ts`：「第◯条」/ 全角编号 / 特約标题识别、跨页拼接；先用干净 PDF 文本写 10 个测试 case 全绿。
- **Day 4（周四）**：切分器抗噪。把 Day 2 的 OCR 噪声输出喂给切分器，补 5+ 个噪声 case（编号误识、行序错乱）；写 `extract-terms.ts` 雏形（金额/月数抽取，复用 normalize.ts）+ 测试。
- **Day 5（周五）**：端到端 spike 页。`/spike/contract`（仿 `/spike/ocr`）：上传 → OCR/PDF → 切分 → 条款 JSON 展示；iPhone Safari 用 `next build && next start` 实测一遍；硬编码 3 条示范规则（違約金/敷金償却/自動更新）验证 scan.ts 接口形状。
