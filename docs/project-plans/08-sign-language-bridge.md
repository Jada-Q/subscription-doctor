# 项目 8：手语的「实时双向桥」

> 端侧、离线、免费的双向手语翻译：摄像头识别手语 → 文字/语音；语音 → 屏幕上的 3D 手语虚拟人。
> 本文是面向单人起步的务实实施计划。基调：**诚实承认局限，先做小而真的东西。**

---

## 1. 一句话定位与目标用户

**一句话定位**：一个完全离线运行在浏览器/手机里的「面对面对话桥」，让聋人与不懂手语的听人在药局、市役所窗口、便利店等 1 对 1 短对话场景中互相理解——不录像、不上传、不收费。

**目标用户**：

- 主要：日常需要与听人进行短事务性对话的聋人/重听者（窗口办事、购物、就医挂号）；
- 次要：愿意配合但不懂手语的听人（店员、窗口职员）——产品必须让"听人那一侧"零学习成本。

**先做哪种手语：日本手语（JSL）**。理由：

| 维度                 | JSL                                                                  | CSL                                           |
| -------------------- | -------------------------------------------------------------------- | --------------------------------------------- |
| 公开数据集           | 几乎没有可商用的公开数据集                                           | 有 SLR500 / CSL-Daily（科研授权，非商用受限） |
| 社区可达性（对本人） | 高：本人面向日本市场开发，可线下接触ろう者团体、手話サークル         | 低：远程接触，共创成本高                      |
| 指拼系统             | 指文字（约 46 基础形 + 浊音/拗音派生），文档齐全                     | 汉语拼音指语 30 形，文档齐全                  |
| 落地场景             | 日本无障碍法规（障害者差別解消法「合理的配慮」）推动窗口场景需求明确 | 场景同样明确但本人不在地                      |

决策逻辑：**这个项目的成败瓶颈不是数据集大小，而是能否与聋人社区持续共创**（见第 6 节）。CSL 的数据优势在 MVP 阶段（指拼 + 小词表，全部自采）用不上，而 JSL 的社区可达性优势从第一周就用得上。架构上保持手语无关（关键点 → 分类器），未来切换/增加 CSL 成本可控。

## 2. 诚实的难度评估

**必须先说清楚：连续手语识别（Continuous Sign Language Recognition / Translation）至今是研究级未解难题。** 不诚实面对这一点，项目会死在第 3 个月。

- 学术现状：在最好的公开基准上（如 PHOENIX-2014T、CSL-Daily），最先进模型的翻译 BLEU 也只有 20–25 左右——这意味着**实验室条件下尚且远达不到"日常对话可用"**，更不用说端侧小模型 + 任意光照 + 任意摄像头角度。
- 手语不是"手的运动"：非手部要素（表情、口型、头部姿态、视线）承担语法功能；JSL 的语序和日语不同，存在分类词谓语、空间指代等结构，**逐词识别 ≠ 翻译**。
- 个体差异大：同一个词不同人打法差异显著，方言（地域差）真实存在。

**因此 MVP 必须主动降级，并对用户明说降级了什么：**

1. **第一档（MVP）：指文字识别**。约 46 个基础静态/准静态手形 + 少量动态派生。这是手形分类问题，单人 + MediaPipe + 小分类器 3 个月内可做到可用精度。指文字真实有用：人名、地名、药品名、外来语在 JSL 中本来就靠指文字。
2. **第二档：孤立词识别（50–100 个高频场景词）**。"お願いします / いくら / 痛い / 薬 / 待つ"等窗口场景词。孤立词（用户打一个词、停顿）是分类问题，不是连续识别。
3. **不做（并在产品里写明）：连续自然手语的句子级翻译。** UI 上明确标注"本应用只能识别指文字和约 N 个单词，不能翻译完整手语句子"。把局限写在脸上是对聋人用户最基本的尊重，也是避免"误译造成伤害"的第一道防线。

## 3. MVP 范围：先做识别，后做虚拟人

**推荐：识别方向（手语→文字）先行。** 理由：

1. **不对称的替代方案**：语音→聋人方向已有"勉强可用"的离线替代（语音转文字给对方看，端侧 STT 成熟）；而手语→听人方向，不懂手语的听人**完全没有**替代手段——这才是桥上缺的那一半。
2. 识别的质量**可量化**（准确率、混淆矩阵），单人可以闭环迭代；虚拟人手语的"自然度/可懂度"只能由聋人评判，在社区共创机制建立之前做合成是闭门造车，且不自然的虚拟人手语在聋人社区有过翻车先例（多个国家的"手语手套/虚拟人"项目因未与社区共创而被抵制）。
3. 合成方向 MVP 期用**降级方案**补位：语音 → 端侧 STT → **大字幕显示**（聋人普遍可读文字），3D 虚拟人作为第二里程碑，且首版只做**指文字虚拟人**（确定性骨骼动画，无歧义、可验证）。

**MVP 范围清单**：

- ✅ 摄像头 → JSL 指文字逐字识别 → 文字串显示 + 可选 TTS
- ✅ 听人语音 → 端侧 STT → 大字号字幕
- ✅ 完全离线（PWA，首次加载后断网可用）、无账号、无上传
- ✅ 候选词展示 + 置信度可视化（见第 8 节风险 1）
- ❌ 连续手语句子翻译、❌ 3D 虚拟人（M3 再做）、❌ 多人对话、❌ 云端任何东西

## 4. 技术架构

```
┌─ 识别链路（手语 → 文字/语音）──────────────────────────────┐
│ Camera (getUserMedia)                                        │
│   → MediaPipe Hands（MVP，仅手部 21 关键点 ×2 手）           │
│     （M2 起换 Holistic：手 + 姿态 + 脸，为非手部要素留路）   │
│   → 关键点归一化（以手腕为原点、按手掌尺度缩放、镜像增广）   │
│   → 时序窗口（30–60 帧滑窗）                                 │
│   → 轻量时序分类器：GRU 或 TCN，参数量 <1M                   │
│     训练：PyTorch → 导出 ONNX → 浏览器 ONNX Runtime Web      │
│   → CTC/投票去重 + 语言侧后处理（指文字串 → 候选词典纠错）   │
│   → 文字显示 + Web Speech Synthesis（本地 TTS）              │
└──────────────────────────────────────────────────────────────┘

┌─ 合成链路（语音 → 字幕/虚拟人）────────────────────────────┐
│ Mic → 端侧 STT（whisper.cpp WASM tiny/base 或 sherpa-onnx）  │
│   → 字幕（MVP）                                              │
│   → M3：文本 → 指文字序列/词序列                             │
│     → Three.js + glTF 骨骼绑定虚拟人（手部全骨骼）           │
│     → 动画片段库（每个指文字/单词一个手工制作的动画 clip）   │
│     → clip 间插值过渡（quaternion slerp），可调语速          │
└──────────────────────────────────────────────────────────────┘
```

关键技术决策：

- **只用关键点，不用原始像素训练分类器**。好处：模型极小（KB–MB 级）、训练数据可以只存关键点（隐私：自采数据不必保存人脸视频）、对光照/背景/肤色鲁棒、跨设备一致。代价：丢失部分手指自遮挡信息——指文字中少数易混对（如形状相近的手形）需靠时序和词典纠错兜底。
- **MediaPipe Hands 先行而非直接上 Holistic**：MVP 只需要手；Holistic 在低端手机上帧率压力大。但归一化与特征接口按 Holistic 的超集设计，避免 M2 重构。
- **虚拟人走"动画片段库"而非生成式合成**：每个指文字一个手工 keyframe 的骨骼动画，由聋人顾问逐个审校。确定性、可审计、不会"幻觉出错误手语"。生成式手语合成（文本→连续动作）是另一个研究级难题，本项目不碰。
- **性能预算**：目标中端 Android（如 4 年前的机型）上端到端 ≥15 FPS；MediaPipe Hands ~10ms/帧（GPU delegate），分类器 <5ms。STT 用 whisper tiny（~75MB），模型按需懒加载并缓存到 Cache Storage。
- **全部 PWA**：Service Worker 缓存模型与资源；无任何网络依赖即可完成核心流程，这本身就是隐私承诺的技术兑现。

## 5. 数据策略

**公开数据集盘点（诚实版）：**

| 数据集             | 语种     | 规模                                         | 对本项目的可用性                                                         |
| ------------------ | -------- | -------------------------------------------- | ------------------------------------------------------------------------ |
| WLASL              | ASL      | ~2000 词孤立词视频                           | ❌ 语种不对，但其关键点预处理流水线/基线代码值得借用；许可仅限非商用研究 |
| MS-ASL             | ASL      | ~1000 词                                     | ❌ 同上                                                                  |
| ChicagoFSWild(+)   | ASL 指拼 | 野外指拼序列                                 | △ 语种不对，但是指拼识别方法论的最佳参考文献来源                         |
| RWTH-PHOENIX-2014T | DGS      | 连续手语（天气预报）                         | ❌ 连续识别基准，MVP 不做连续；用于校准对难度的认知                      |
| CSL-Daily / SLR500 | CSL      | 大规模                                       | △ 科研授权、非商用限制；若未来做 CSL 再申请                              |
| JSL 公开数据       | JSL      | **近乎空白**（零星科研小数据，无可商用大集） | —— 这就是要自采的原因                                                    |

**结论：JSL 指文字 + 50–100 孤立词的训练数据必须自采，而这在降级后的范围内是完全可行的。** 估算：46 指文字 × 每形 200 样本（多人、多角度、左右手）≈ 1 万条关键点序列；单条采集 2 秒，工具顺手的话一人一小时可采数百条。

**自采三原则：**

1. **先自己和朋友采"脏数据"把流水线跑通**（M1），但明确这批数据只用于调通代码，**不作为精度结论依据**——听人模仿的指文字和母语者的打法有系统性差异。
2. **真实训练/测试集必须来自聋人协作者**（M2 起），与第 6 节共创机制绑定：有偿采集、知情同意书（明确用途、可随时撤回）、**默认只保存关键点不保存原始视频**（除非本人书面同意），原始视频如保存则本地加密、不出采集设备。
3. **测试集按人划分（signer-independent split）**：训练和测试不共享打手语的人，否则准确率是自欺欺人。这一条写进 CI。

数据采集工具本身就是产品的一部分：做一个网页版"采集模式"（显示目标手形 → 倒计时 → 录关键点 → 本人确认），让协作者在自己设备上自助采集，数据以文件形式导出交付——同样不经过服务器。

## 6. 与聋人社区的共创机制

原则只有一条：**"Nothing about us without us"。聋人是设计者和审校者，不是测试对象。** 具体接触方案：

1. **第 1 个月：建立第一个接触点。**
   - 查询所在都道府県的**聴覚障害者協会 / ろうあ連盟地方支部**公开窗口，以书面（邮件/Form）自我介绍：个人开发者、免费离线工具、求 1 名有偿顾问。附 demo 视频（哪怕只是 MediaPipe 骨架可视化）证明不是空想。
   - 同时接触门槛更低的渠道：地域**手話サークル**（听人和聋人混合的学习会，公民馆常有）、大学手話部、手話通訳士。手話サークル是最现实的第一站——氛围友好，且能介绍聋人成员。
   - X/YouTube 上活跃的聋人创作者：私信附 demo，明说"付费请教 1 小时"。
2. **聘请 1 名聋人顾问（有偿，按小时或按月）**，角色是**共同设计者**：每两周一次视频会（笔谈/手语通译/字幕皆可），职责包括：审定 MVP 词表（什么词在窗口场景真正高频）、审校虚拟人每一个动画片段、判定"这个识别错误是滑稽还是冒犯"。预算紧张也不能省这笔钱——无偿索取聋人劳动是这一领域项目失败的头号原因。
3. **M2 起组织小规模采集会**：通过协会/サークル招募 5–10 名聋人协作者，每人 1–2 小时有偿采集 + 试用反馈。地点选对方熟悉的场所（协会活动室）。
4. **公开透明**：项目仓库开源（代码 MIT；数据另行授权，归属协作者集体决定）、用通俗日语写一页"这个工具能做什么/不能做什么"、所有宣传材料先经顾问过目——避免任何"科技拯救聋人"的叙事，定位是"给听人那一侧补课的工具"。
5. **退出机制**：如果社区反馈是"这个方向本身不被需要"，**接受并转向**（例如转向纯指文字学习工具）。把这一条写进计划，是诚实的一部分。

## 7. 里程碑（4 阶段）

### M1：骨架闭环（第 1–6 周）

- 交付物：网页 demo——摄像头 → MediaPipe Hands → 实时识别 **10 个指文字**（自己+朋友的脏数据训练），离线 PWA 可安装。
- 验证标准：本人设备上 ≥15 FPS；10 类自测准确率 ≥90%（明知此数字不算数，仅验证流水线）；采集工具可用，他人 30 分钟内能自助采完 50 条样本。

### M2：真数据、真用户（第 7–14 周）

- 交付物：聋人顾问到位；5+ 名聋人协作者完成采集；**全部 46 基础指文字**识别上线；语音→字幕链路（whisper WASM）上线；signer-independent 测试集建立。
- 验证标准：signer-independent 指文字准确率 ≥85%（top-1）/ ≥95%（top-3 候选）；2 名聋人协作者用它完成一次模拟窗口对话并给出结构化反馈；端到端延迟（出手到上屏）<500ms。

### M3：双向成形（第 15–24 周）

- 交付物：50 个场景孤立词识别；Three.js 指文字虚拟人（46 个动画片段，全部经顾问审校签字）；语音→虚拟人指文字播放链路。
- 验证标准：孤立词 signer-independent top-1 ≥80%；虚拟人指文字可懂度测试——3 名未参与项目的聋人读取虚拟人拼出的 20 个词，正读率 ≥90%；中端 Android 实机全链路可用。

### M4：公开 Beta（第 25–32 周）

- 交付物：公开网址 + 应用内"能力边界"说明页（日语，顾问审定）；面向手話サークル的 20 人试用计划；问题反馈通道（本地导出反馈文件，仍不经服务器）。
- 验证标准：20 名真实用户（含 ≥8 名聋人）完成至少一次真实场景使用；收集 ≥50 条结构化反馈；据此决定 v2 方向（扩词表 vs. 做 CSL vs. 转向）。

## 8. 主要风险与对策

1. **【必含】识别准确率不达标导致误解 → 真实伤害**（药名、金额、地名拼错，在医疗/办事场景后果严重）。
   对策：(a) UI 永远显示 top-3 候选 + 置信度条，低置信度时显示"？"而非硬猜；(b) 逐字确认交互——打完一个指文字，屏幕回显，打"取消"手形可删除，**用户确认过的才进入句子**；(c) 应用内醒目免责声明（顾问审定措辞）：医疗、法律、金钱等关键信息**必须**用其他方式二次确认；(d) 词典约束解码：指文字串优先匹配场景词典，无法匹配时如实显示原始字母串而不强行纠错。
2. **JSL 数据自采规模不足，模型对采集环境过拟合**。
   对策：只用关键点特征天然削弱背景过拟合；强制 signer-independent 评测；几何数据增广（旋转/镜像/速度扰动/关键点抖动）；词表宁小勿大——46 指文字做到 95% 远胜 300 词做到 60%。
3. **虚拟人手语不自然/不准确，冒犯聋人社区，项目声誉死亡**（前车之鉴众多）。
   对策：M3 之前不公开任何虚拟人内容；每个动画片段由聋人顾问逐个审校并有否决权；首版只做指文字（确定性高、争议小）；宣传上永远不说"翻译手语"，只说"指文字显示辅助"。
4. **低端设备性能不足，目标用户恰恰用不起来**。
   对策：性能预算从 M1 写死（中端 4 年前 Android 为基准机）；MediaPipe Hands 而非 Holistic 起步；分辨率自适应降级（720p→480p）；帧率不足时 UI 明确提示而非静默变卡。
5. **社区信任建立失败：被视为又一个"听人拍脑袋项目"**。
   对策：第 6 节机制前置到 M1/M2 之交而非产品做完才找人；顾问有偿且有否决权；开源 + 数据归属透明；准备好听到"不需要"并真的转向。
6. **单人项目范围失控（连续识别的诱惑）**。
   对策：本文第 2 节即合同——任何"要不要试试句子识别"的念头，先回来重读第 2 节；每个里程碑的验证标准是数字，不达标不进下一阶段。

## 9. 第一周行动清单（单人，具体到天）

- **Day 1（周一）**：环境与可行性。跑通 MediaPipe Hands 官方 Web demo；新建仓库（Vite + TypeScript + PWA 模板）；写 50 行页面：摄像头 → 21 关键点实时叠加渲染。验收：手机浏览器上看到自己的手部骨架，≥15 FPS。
- **Day 2（周二）**：学指文字 + 定 schema。系统过一遍 JSL 指文字表（46 基础形），亲手学会前 10 个；设计关键点序列的存储格式（JSON：帧数组 × 21 点 × (x,y,z) + 标签 + 元数据）；写归一化函数（腕部原点、手掌尺度、镜像）+ 单元测试。
- **Day 3（周三）**：采集工具。做"采集模式"页面：显示目标指文字图示 → 3 秒倒计时 → 录 2 秒关键点 → 回放确认 → 存 IndexedDB → 可导出 JSON 文件。验收：自己 30 分钟采完 10 类 × 30 条。
- **Day 4（周四）**：训练第一个模型。PyTorch：小 GRU（输入 63 维 × T 帧 → 10 类）；自采数据训练；导出 ONNX；笔记本上确认推理正确。验收：留出集准确率 >90%（脏数据，仅验流水线）。
